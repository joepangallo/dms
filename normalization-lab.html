Clean up a messy database table in three steps

We will begin with an unnormalized sales table. Then we will improve it in order: first normal form, second normal form, and third normal form.

This table is unnormalized because its items cell holds more than one item record.

Why there is no primary key here

  • One row is one invoice, so invoice_num does tell you which row you are looking at.
  • But it cannot reach one item. There is no key value that means the quantity of DG04 on invoice 50710.
  • item_id is not a column. It is text inside the items cell, and a value that is not a column of its own cannot be part of a key.
  • A table that still contains a repeating group is not yet a proper relation, so the database cannot enforce a primary key on it. 1NF is the step that makes a real key possible.

What is a list or repeating group?

A list is several values stored together inside one cell. Above, item IDs CF21 and DG04 are both inside invoice 50710’s items cell.

A repeating group is the same set of facts stored more than once in one row. It could be a list, or it could use columns such as item_1, quantity_1, item_2, and quantity_2.

An item has no row of its ownThe quantity for DG04 is buried inside invoice 50710’s items cell.
The database cannot check each itemIt cannot easily require every embedded quantity to be greater than zero.
Searching is difficultFinding all invoices with CF21 requires reading and splitting the list inside every row.
Step 1

First normal form: one value per cell

1NF removes lists and repeating groups. Each item on an invoice receives its own row.

1NF rule

Every cell should contain one value, and every row should have one clear meaning. After this step, one row means one item on one invoice.

How to change the table

  1. Describe the starting row.One SALES_REPORT row represents one whole invoice.
  2. Find the repeating group.The items cell contains several item IDs, descriptions, quantities, and prices.
  3. Create one row for each item.Invoice 50710 becomes one row for CF21 and another row for DG04.
  4. Repeat invoice information temporarily.Both new rows keep invoice 50710’s date and customer information. Later steps remove this repetition.
  5. Use both IDs as the row key.invoice_num alone can repeat, and item_id alone can repeat. Together, they identify one item on one invoice.
After 1NFThe item list is gone. Every item has its own row and its own quantity and price cells.
We are not finished.Invoice, customer, and item descriptions still repeat across rows. 2NF and 3NF will fix that.

What changed in the design?

  • The single items column was replaced by four columns: item_id, item_description, category, and num_ordered with quoted_price.
  • SALES_REPORT had no primary key the database could enforce. Now that item_id is a real column, SALES_LINE can have one.
  • One key part is not enough, because one row is now one item on one invoice. invoice_num repeats and item_id repeats, so the key needs both.
  • Two PK badges mean the two IDs work together as one primary key: key part 1 plus key part 2.
  • There is still one table. 2NF will split it into INVOICE, ITEM, and INVOICE_LINE.
Step 2

Second normal form: use the whole two-part key

The SALES_LINE key has two parts. 2NF moves facts that need only one part of that key.

2NF rule

Some row keys use two columns. Every other fact in that table should need both columns. If invoice_num alone tells us a fact, move it to an invoice table. If item_id alone tells us a fact, move it to an item table.

How to split the 1NF table

  1. Look at the two-part key.The SALES_LINE key is (invoice_num, item_id).
  2. Test invoice_num by itself.It already tells us the invoice date and customer information.
  3. Move invoice facts to INVOICE.Use invoice_num as the INVOICE primary key.
  4. Test item_id by itself.It already tells us the item description and category, so move those facts to ITEM.
  5. Keep line facts in INVOICE_LINE.Quantity and quoted price need both the invoice number and item ID.
After 2NFInvoice facts, item facts, and invoice-line facts now have separate tables.
One problem remains.Customer name and city are still inside INVOICE, even though they describe a customer.
invoice_num alone tells usinvoice_date and customer information
item_id alone tells usitem_description and category
invoice_num + item_id tell usnum_ordered and quoted_price

Step 3

Third normal form: one kind of thing per table

3NF moves customer details out of INVOICE because those details describe the customer, not the invoice.

3NF rule

Store each fact with the ID that directly identifies it. customer_num tells us the customer name and city, so those customer facts belong in a CUSTOMER table.

How to finish the design

  1. Look inside INVOICE.invoice_num tells us customer_num.
  2. Follow the customer number.customer_num tells us the customer name and city.
  3. Create CUSTOMER.Use customer_num as its primary key.
  4. Move customer details.Put customer_name and customer_city in CUSTOMER.
  5. Keep the connection.Leave customer_num in INVOICE as a foreign key pointing to CUSTOMER.
After 3NFEach table describes one kind of thing, and the ID columns connect the tables.

Quick review

What each step fixed

Each step solves a different problem. The steps must be completed in order.

StepSimple questionWhat we changed
1NFDoes any cell contain a list or repeating group?We turned the items list into one SALES_LINE row per item.
2NFWith a two-part key, does a fact need only one key part?We moved invoice facts to INVOICE and item facts to ITEM.
3NFDoes this table contain facts about a different kind of thing?We moved customer name and city from INVOICE to CUSTOMER.
Optional implementation

SQL for the tables after 3NF

The SQL uses primary keys to identify rows and foreign keys to keep the table connections valid.

Open the CREATE TABLE statements
normalized-schema.sql
CREATE TABLE CUSTOMER (
  customer_num  CHAR(4) PRIMARY KEY,
  customer_name VARCHAR(80) NOT NULL,
  customer_city VARCHAR(40) NOT NULL
);

CREATE TABLE ITEM (
  item_id          CHAR(4) PRIMARY KEY,
  item_description VARCHAR(100) NOT NULL,
  category         VARCHAR(30) NOT NULL
);

CREATE TABLE INVOICE (
  invoice_num  CHAR(5) PRIMARY KEY,
  invoice_date DATE NOT NULL,
  customer_num CHAR(4) NOT NULL,
  FOREIGN KEY (customer_num) REFERENCES CUSTOMER(customer_num)
);

CREATE TABLE INVOICE_LINE (
  invoice_num  CHAR(5) NOT NULL,
  item_id      CHAR(4) NOT NULL,
  num_ordered  SMALLINT NOT NULL CHECK (num_ordered > 0),
  quoted_price DECIMAL(7,2) NOT NULL,
  PRIMARY KEY (invoice_num, item_id),
  FOREIGN KEY (invoice_num) REFERENCES INVOICE(invoice_num),
  FOREIGN KEY (item_id) REFERENCES ITEM(item_id)
);
