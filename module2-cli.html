Doing the Module 2 labs at the command line

Every SQL statement from Lesson 2-5, run in a real terminal against a real database file, with the output you should expect at each step. No server, no accounts, no browser.

The browser labs in Lesson 2-5 run SQLite compiled into the page. This walkthrough does exactly the same work with the sqlite3 command-line tool. The SQL is identical, character for character — what changes is that you own the database file, so your work persists between sessions and you can hand it in.

One difference worth knowing up front

In the browser, every exercise box has its own private database, which is why each one starts from a preloaded dataset. At the command line you work in one file and each statement builds on the last. That is closer to real life, and it means the order of these steps matters.

Part 1Get the sqlite3 tool

You need the command-line program called sqlite3. Pick your operating system.

1

Open Terminal and check it is there

macOS ships with sqlite3 already installed. Open Terminal (press Cmd+Space, type Terminal, press Enter) and run:

Terminal

What you should see

Part 3The sqlite3 survival kit

Two kinds of thing get typed at the sqlite> prompt, and telling them apart saves a lot of confusion.

KindLooks likeRule
SQL statementsSELECT COUNT(*) FROM LEASE_REPORT; Must end with a semicolon. Until you type one, SQLite keeps waiting and shows ...>.
Dot commands.tables Instructions to the tool itself, not the database. One per line, no semicolon.

The dot commands worth knowing for these labs:

CommandWhat it does
.headers onShow column names above results. Do this every session.
.mode boxDraw results in a bordered table. Makes everything readable.
.tablesList the tables in the database right now.
.schema TABLENAMEShow the CREATE TABLE statement behind a table.
.read filename.sqlRun every statement in a file.
.quitLeave sqlite3 and go back to the terminal.
Stuck at a ...> prompt?

You forgot a semicolon. Type one and press Enter. If you are truly stuck, press Ctrl+C to abandon the line.

Part 4Mini-lab 1 — First normal form

StayWell's flat lease report has a list crammed into PAYMENT_DATES. You will ask it three ordinary questions, watch it answer all three wrong, then fix the table and ask again.

4

Create the database and load the flat report

This creates a new file called staywell.db and drops you at the sqlite> prompt:

Terminal
sqlite3 staywell.db

Now set up readable output and load the data:

sqlite> prompt
.headers on
.mode box
.read staywell_flat.sql
.tables
What you should see
LEASE_REPORT

One table, three rows. If you get "cannot open" the file is not in this folder — check with ls (macOS/Linux) or dir (Windows).

5

Question 1 — how many payments has StayWell received?

The true answer is 4. Ask the table:

sqlite> prompt
SELECT COUNT(*) AS ROWS_IN_THE_REPORT
FROM LEASE_REPORT;
What you should see
┌────────────────────┐
│ ROWS_IN_THE_REPORT │
├────────────────────┤
│ 3                  │
└────────────────────┘

It says 3. Nothing failed and nothing was flagged — 3 is the number of rows, and rows stopped meaning payments the moment somebody typed a comma into a cell.

6

Question 2 — what is the most recent payment date?

The true answer is 2026-09-01.

sqlite> prompt
SELECT MAX(PAYMENT_DATES) AS LATEST_PAYMENT
FROM LEASE_REPORT;
What you should see
┌────────────────────────┐
│     LATEST_PAYMENT     │
├────────────────────────┤
│ 2026-08-01, 2026-09-01 │
└────────────────────────┘

This is the one that changes minds. It did not return a date at all — it returned the whole string, because SQLite compared text and that string sorted highest. A report built on this would print that into a box labelled "latest payment".

7

Question 3 — how much rent have we collected?

There is no expression to write. The best SQL can do is hand the lists back:

sqlite> prompt
SELECT STUDENT_ID, MONTHLY_RENT, PAYMENT_DATES
FROM LEASE_REPORT;
What you should see
┌────────────┬──────────────┬────────────────────────┐
│ STUDENT_ID │ MONTHLY_RENT │     PAYMENT_DATES      │
├────────────┼──────────────┼────────────────────────┤
│ S001       │ 595          │ 2026-08-01, 2026-09-01 │
│ S002       │ 450          │ 2026-08-01             │
│ S003       │ 725          │ 2026-08-01             │
└────────────┴──────────────┴────────────────────────┘

A person has to count them by eye. That is not a database answering a question.

8

Fix it — one row per payment

1NF says every cell holds one value. Give each payment its own row, in its own table:

sqlite> prompt
CREATE TABLE PAYMENT_1NF (
    STUDENT_ID    CHAR(4),
    PAYMENT_DATE  DATE,
    PRIMARY KEY (STUDENT_ID, PAYMENT_DATE)
);

INSERT INTO PAYMENT_1NF VALUES ('S001', '2026-08-01');
INSERT INTO PAYMENT_1NF VALUES ('S001', '2026-09-01');
INSERT INTO PAYMENT_1NF VALUES ('S002', '2026-08-01');
INSERT INTO PAYMENT_1NF VALUES ('S003', '2026-08-01');

CREATE TABLE LEASE_1NF AS
SELECT STUDENT_ID, STUDENT_NAME, PROPERTY_ID, PROPERTY_NAME,
       MANAGER_NAME, ROOM_NUM, ROOM_TYPE, MONTHLY_RENT
FROM LEASE_REPORT;

Confirm the two new tables exist:

sqlite> prompt
.tables
What you should see
LEASE_1NF     LEASE_REPORT  PAYMENT_1NF

SQLite says nothing when a CREATE or INSERT succeeds. Silence means it worked.

9

Ask all three questions again

sqlite> prompt
SELECT COUNT(*) AS PAYMENTS_RECEIVED FROM PAYMENT_1NF;
What you should see
┌───────────────────┐
│ PAYMENTS_RECEIVED │
├───────────────────┤
│ 4                 │
└───────────────────┘
sqlite> prompt
SELECT MAX(PAYMENT_DATE) AS LATEST_PAYMENT FROM PAYMENT_1NF;

┌────────────────┐
│ LATEST_PAYMENT │

├────────────┼───────────────┼───────────────┼───────────┤
│ S001       │ Trang Nguyen  │ 2             │ 1190      │

Every answer is now right, and notice why: nothing clever happened. There are four rows and each row is one payment.

14

Start a clean database and test the dependencies

Terminal
sqlite3 kimtay.db
sqlite> prompt
.headers on
.mode box
.read kimtay_flat.sql

The key is (INVOICE_NUM, ITEM_ID). 2NF asks which columns need both halves. Do not guess — test it. If INVOICE_NUM really determines the date, no invoice number can carry two different dates:

sqlite> prompt
SELECT INVOICE_NUM,
       COUNT(DISTINCT INVOICE_DATE) AS DATES,
       COUNT(DISTINCT CUSTOMER_NUM) AS CUSTOMERS
FROM INVOICE_FLAT
GROUP BY INVOICE_NUM;
What you should see
┌─────────────┬───────┬───────────┐
│ INVOICE_NUM │ DATES │ CUSTOMERS │
├─────────────┼───────┼───────────┤
│ 50710       │ 1     │ 1         │
│ 50711       │ 1     │ 1         │
│ 50712       │ 1     │ 1         │
└─────────────┴───────┴───────────┘

Every count is 1, so INVOICE_NUM alone fixes both. That is a partial dependency.

15

The test that fails — and why that matters

Run the same shape of test on the quantity:

sqlite> prompt
SELECT ITEM_ID,
       COUNT(DISTINCT NUM_ORDERED) AS QUANTITIES
FROM INVOICE_FLAT
GROUP BY ITEM_ID;
What you should see
┌─────────┬────────────┐
│ ITEM_ID │ QUANTITIES │
├─────────┼────────────┤
│ AV07    │ 1          │
│ CF21    │ 2          │
│ DG04    │ 1          │
│ FT88    │ 1          │
│ GR15    │ 1          │
└─────────┴────────────┘

CF21 comes back with a 2, because someone ordered 3 of it on one invoice and 2 on another. ITEM_ID alone does not fix the quantity, so NUM_ORDERED needs the whole key and stays put. That single 2 is the difference between a column that must move and one that must not.

16

Split off the partial dependencies (2NF)

sqlite> prompt
CREATE TABLE INVOICE_2NF (
    INVOICE_NUM    CHAR(5)   PRIMARY KEY,
    INVOICE_DATE   DATE,
    CUSTOMER_NUM   CHAR(4),
    CUSTOMER_NAME  VARCHAR(35),
    CUSTOMER_CITY  VARCHAR(15)
);
INSERT INTO INVOICE_2NF
SELECT DISTINCT INVOICE_NUM, INVOICE_DATE, CUSTOMER_NUM, CUSTOMER_NAME, CUSTOMER_CITY
FROM INVOICE_FLAT;

CREATE TABLE ITEM_2NF (
    ITEM_ID      CHAR(4)      PRIMARY KEY,
    DESCRIPTION  VARCHAR(30),
    CATEGORY     VARCHAR(15)
);
INSERT INTO ITEM_2NF
SELECT DISTINCT ITEM_ID, ITEM_DESCRIPTION, CATEGORY FROM INVOICE_FLAT;

CREATE TABLE INVOICE_LINE_2NF (
    INVOICE_NUM   CHAR(5),
    ITEM_ID       CHAR(4),
    NUM_ORDERED   SMALLINT,
    QUOTED_PRICE  DECIMAL(7,2),
    PRIMARY KEY (INVOICE_NUM, ITEM_ID)
);
INSERT INTO INVOICE_LINE_2NF
SELECT INVOICE_NUM, ITEM_ID, NUM_ORDERED, QUOTED_PRICE FROM INVOICE_FLAT;
sqlite> prompt
SELECT (SELECT COUNT(*) FROM INVOICE_2NF)      AS INVOICE_ROWS,
       (SELECT COUNT(*) FROM ITEM_2NF)         AS ITEM_ROWS,
       (SELECT COUNT(*) FROM INVOICE_LINE_2NF) AS LINE_ROWS;
What you should see
┌──────────────┬───────────┬───────────┐
│ INVOICE_ROWS │ ITEM_ROWS │ LINE_ROWS │
├──────────────┼───────────┼───────────┤
│ 3            │ 5         │ 6         │
└──────────────┴───────────┴───────────┘

Six repetitive rows became 3 invoices, 5 items and 6 lines. CF21's description is now written down exactly once, so it can only ever be renamed once.

17

Remove the transitive dependency (3NF)

INVOICE_2NF still repeats itself: CUSTOMER_NAME is fixed by CUSTOMER_NUM, which is not this table's key. Check it the same way, then split:

sqlite> prompt
SELECT CUSTOMER_NUM,
       COUNT(DISTINCT CUSTOMER_NAME) AS NAMES,
       COUNT(DISTINCT CUSTOMER_CITY) AS CITIES
FROM INVOICE_2NF
GROUP BY CUSTOMER_NUM;
sqlite> prompt
CREATE TABLE CUSTOMER_3NF (
    CUSTOMER_NUM   CHAR(4)      PRIMARY KEY,
    CUSTOMER_NAME  VARCHAR(35),
    CUSTOMER_CITY  VARCHAR(15)
);
INSERT INTO CUSTOMER_3NF
SELECT DISTINCT CUSTOMER_NUM, CUSTOMER_NAME, CUSTOMER_CITY FROM INVOICE_2NF;

CREATE TABLE INVOICE_3NF (
    INVOICE_NUM   CHAR(5)  PRIMARY KEY,
    INVOICE_DATE  DATE,
    CUSTOMER_NUM  CHAR(4),
    FOREIGN KEY (CUSTOMER_NUM) REFERENCES CUSTOMER_3NF(CUSTOMER_NUM)
);
INSERT INTO INVOICE_3NF
SELECT INVOICE_NUM, INVOICE_DATE, CUSTOMER_NUM FROM INVOICE_2NF;
18

Prove you lost nothing

Stitch the four small tables back into one wide table, then ask the database whether it matches the original:

sqlite> prompt
CREATE TABLE REBUILT AS
SELECT il.INVOICE_NUM, il.ITEM_ID, i.INVOICE_DATE, c.CUSTOMER_NUM,
       c.CUSTOMER_NAME, c.CUSTOMER_CITY, it.DESCRIPTION AS ITEM_DESCRIPTION,
       it.CATEGORY, il.NUM_ORDERED, il.QUOTED_PRICE
FROM INVOICE_LINE_2NF il
JOIN INVOICE_3NF  i  ON il.INVOICE_NUM = i.INVOICE_NUM
JOIN CUSTOMER_3NF c  ON i.CUSTOMER_NUM = c.CUSTOMER_NUM
JOIN ITEM_2NF     it ON il.ITEM_ID     = it.ITEM_ID;
sqlite> prompt
SELECT CASE
         WHEN (SELECT COUNT(*) FROM (SELECT * FROM REBUILT EXCEPT SELECT * FROM INVOICE_FLAT)) = 0
          AND (SELECT COUNT(*) FROM (SELECT * FROM INVOICE_FLAT EXCEPT SELECT * FROM REBUILT)) = 0
         THEN 'LOSSLESS - the four 3NF tables rebuild the report exactly'
         ELSE 'LOSSY - the split changed the data'
       END AS VERDICT;
What you should see
┌───────────────────────────────────────────────────────────┐
│                          VERDICT                          │
├───────────────────────────────────────────────────────────┤
│ LOSSLESS - the four 3NF tables rebuild the report exactly │
└───────────────────────────────────────────────────────────┘

EXCEPT lists rows on the left that are missing on the right, so running it both ways asks "did we lose anything?" and "did we invent anything?" at once. Both come back empty.

And look where you landed — INVOICE, INVOICE_LINE, ITEM, CUSTOMER. That is the KimTay schema from Module 1, produced by the flat report plus three mechanical rules.

sqlite> prompt
.quit

StayWell's property sheet has all three faults in it. Take it to 3NF yourself. A self-check is provided that grades your work in one query, and the answer is at the bottom of this page — try it first.

sqlite> prompt
.headers on
.mode box
.read property_sheet.sql
SELECT * FROM PROPERTY_SHEET;
20

Build four tables, with these exact names

The self-check looks for these, so match the names and columns:

  • MY_MANAGER — MANAGER_ID primary key, MANAGER_NAME, MANAGER_PHONE
  • MY_PROPERTY — PROPERTY_ID primary key, PROPERTY_NAME, PROPERTY_CITY, MANAGER_ID foreign key
  • MY_ROOM — composite primary key (PROPERTY_ID, ROOM_NUM), ROOM_TYPE, MONTHLY_RENT, MAX_OCCUPANTS; PROPERTY_ID also a foreign key
  • MY_AMENITY — composite primary key (PROPERTY_ID, AMENITY); PROPERTY_ID also a foreign key

Two techniques save typing. INSERT INTO ... SELECT DISTINCT ... fills a table straight from the sheet, so you never retype a value. The amenities are the one part you type by hand, because splitting a list is exactly what SQL is bad at.

21

Grade yourself

Paste this whole thing at the prompt. It is one statement and returns one table, one row per check:

sqlite> prompt
WITH EXPECTED_AMENITY(PROPERTY_ID, AMENITY) AS (VALUES
       ('P100','Laundry'), ('P100','Parking'),
       ('P200','Laundry'), ('P200','Gym'), ('P200','Parking')),
     REBUILT AS (
       SELECT p.PROPERTY_ID, p.PROPERTY_NAME, p.PROPERTY_CITY,
              m.MANAGER_ID, m.MANAGER_NAME, m.MANAGER_PHONE,
              r.ROOM_NUM, r.ROOM_TYPE, r.MONTHLY_RENT, r.MAX_OCCUPANTS
       FROM MY_ROOM r
       JOIN MY_PROPERTY p ON r.PROPERTY_ID = p.PROPERTY_ID
       JOIN MY_MANAGER  m ON p.MANAGER_ID  = m.MANAGER_ID),
     SHEET AS (
       SELECT PROPERTY_ID, PROPERTY_NAME, PROPERTY_CITY, MANAGER_ID, MANAGER_NAME,
              MANAGER_PHONE, ROOM_NUM, ROOM_TYPE, MONTHLY_RENT, MAX_OCCUPANTS
       FROM PROPERTY_SHEET)
SELECT '1. MY_MANAGER  - one row per manager' AS CHECK_NAME,
       CASE WHEN (SELECT COUNT(*) FROM MY_MANAGER) = 2 THEN 'PASS' ELSE 'FAIL' END AS RESULT,
       'expected 2, found ' || (SELECT COUNT(*) FROM MY_MANAGER) AS DETAIL
UNION ALL
SELECT '2. MY_PROPERTY - one row per property',
       CASE WHEN (SELECT COUNT(*) FROM MY_PROPERTY) = 2 THEN 'PASS' ELSE 'FAIL' END,
       'expected 2, found ' || (SELECT COUNT(*) FROM MY_PROPERTY)
UNION ALL
SELECT '3. MY_ROOM     - one row per room',
       CASE WHEN (SELECT COUNT(*) FROM MY_ROOM) = 5 THEN 'PASS' ELSE 'FAIL' END,
       'expected 5, found ' || (SELECT COUNT(*) FROM MY_ROOM)
UNION ALL
SELECT '4. MY_AMENITY  - one row per amenity',
       CASE WHEN (SELECT COUNT(*) FROM MY_AMENITY) = 5 THEN 'PASS' ELSE 'FAIL' END,
       'expected 5, found ' || (SELECT COUNT(*) FROM MY_AMENITY)
UNION ALL
SELECT '5. Primary and foreign keys declared',
       CASE WHEN
         (SELECT COUNT(*) FROM pragma_table_info('MY_MANAGER')  WHERE name='MANAGER_ID'  AND pk=1) = 1 AND
         (SELECT COUNT(*) FROM pragma_table_info('MY_PROPERTY') WHERE name='PROPERTY_ID' AND pk=1) = 1 AND
         (SELECT COUNT(*) FROM pragma_table_info('MY_ROOM')     WHERE name='PROPERTY_ID' AND pk=1) = 1 AND
         (SELECT COUNT(*) FROM pragma_table_info('MY_ROOM')     WHERE name='ROOM_NUM'    AND pk=2) = 1 AND
         (SELECT COUNT(*) FROM pragma_table_info('MY_AMENITY')  WHERE name='PROPERTY_ID' AND pk=1) = 1 AND
         (SELECT COUNT(*) FROM pragma_table_info('MY_AMENITY')  WHERE name='AMENITY'     AND pk=2) = 1 AND
         EXISTS (SELECT 1 FROM pragma_foreign_key_list('MY_PROPERTY') WHERE "table"='MY_MANAGER') AND
         EXISTS (SELECT 1 FROM pragma_foreign_key_list('MY_ROOM')     WHERE "table"='MY_PROPERTY') AND
         EXISTS (SELECT 1 FROM pragma_foreign_key_list('MY_AMENITY')  WHERE "table"='MY_PROPERTY')
       THEN 'PASS' ELSE 'FAIL' END,
       'composite keys on MY_ROOM and MY_AMENITY, three foreign keys'
UNION ALL
SELECT '6. Amenity values match the source',
       CASE WHEN NOT EXISTS (SELECT * FROM EXPECTED_AMENITY EXCEPT SELECT PROPERTY_ID, AMENITY FROM MY_AMENITY)
             AND NOT EXISTS (SELECT PROPERTY_ID, AMENITY FROM MY_AMENITY EXCEPT SELECT * FROM EXPECTED_AMENITY)
       THEN 'PASS' ELSE 'FAIL' END,
       'each amenity on the right property, none missing or extra'
UNION ALL
SELECT '7. Your tables rebuild the sheet exactly',
       CASE WHEN NOT EXISTS (SELECT * FROM REBUILT EXCEPT SELECT * FROM SHEET)
             AND NOT EXISTS (SELECT * FROM SHEET   EXCEPT SELECT * FROM REBUILT)
       THEN 'PASS' ELSE 'FAIL' END,
       'nothing lost and nothing invented by the split';

-- Create referenced parent tables before child tables so the inserts also work
-- when foreign-key enforcement is enabled.
-- ===== 3NF: MANAGER_NAME and MANAGER_PHONE depend on MANAGER_ID =====
CREATE TABLE MY_MANAGER (
    MANAGER_ID     CHAR(3)      PRIMARY KEY,
    MANAGER_NAME   VARCHAR(30)  NOT NULL,
    MANAGER_PHONE  CHAR(12)
);
INSERT INTO MY_MANAGER
SELECT DISTINCT MANAGER_ID, MANAGER_NAME, MANAGER_PHONE FROM PROPERTY_SHEET;

-- ===== 2NF: property facts depend on PROPERTY_ID alone =====
-- The sheet key is (PROPERTY_ID, ROOM_NUM). PROPERTY_NAME, PROPERTY_CITY and
-- MANAGER_ID are fixed by PROPERTY_ID by itself: partial dependencies.
CREATE TABLE MY_PROPERTY (
    PROPERTY_ID    CHAR(4)      PRIMARY KEY,
    PROPERTY_NAME  VARCHAR(30)  NOT NULL,
    PROPERTY_CITY  VARCHAR(15),
    MANAGER_ID     CHAR(3),
    FOREIGN KEY (MANAGER_ID) REFERENCES MY_MANAGER(MANAGER_ID)
);
INSERT INTO MY_PROPERTY
SELECT DISTINCT PROPERTY_ID, PROPERTY_NAME, PROPERTY_CITY, MANAGER_ID
FROM PROPERTY_SHEET;

-- Only the per-room facts need both halves of the key, so they are what is left.
CREATE TABLE MY_ROOM (
    PROPERTY_ID    CHAR(4),
    ROOM_NUM       CHAR(3),
    ROOM_TYPE      VARCHAR(10),
    MONTHLY_RENT   DECIMAL(7,2),
    MAX_OCCUPANTS  SMALLINT,
    PRIMARY KEY (PROPERTY_ID, ROOM_NUM),
    FOREIGN KEY (PROPERTY_ID) REFERENCES MY_PROPERTY(PROPERTY_ID)
);
INSERT INTO MY_ROOM
SELECT PROPERTY_ID, ROOM_NUM, ROOM_TYPE, MONTHLY_RENT, MAX_OCCUPANTS
FROM PROPERTY_SHEET;

-- ===== 1NF: the AMENITIES list becomes one row per amenity =====
CREATE TABLE MY_AMENITY (
    PROPERTY_ID  CHAR(4),
    AMENITY      VARCHAR(15),
    PRIMARY KEY (PROPERTY_ID, AMENITY),
    FOREIGN KEY (PROPERTY_ID) REFERENCES MY_PROPERTY(PROPERTY_ID)
);
